# 功能开关映射：Windows / Python 实现依据

分析对象为本地欢律 17.6.5（com.heytap.headset），APK SHA-256：`eacb314e092cfb6c2f075eee834498412255cadf184978f3dc16400f6e1dd5d4`。以下是 APK 中观察到的协议与业务映射；尚未用 OPPO Enco Free4 真机验证，不能据此断言该型号支持所有开关。

## 可实现的核心映射

`com.oplus.melody.model.repository.earphone.x.accept` 的 refreshSwitch 分支按 FeatureSwitchInfo.featureType 更新具名状态字段。此映射直接出自代码，非由字符串相似性猜测。Evidence：`ev_140dda3cf7f674e376a8f827904af7db32a51c566e3d335b49eae7f98d9f33e3`（feature-refresh.java/json）。

| featureId | 业务功能 | 更新字段 | UI 发送交叉验证 |
|---|---|---|---|
| 6 / 0x06 | 游戏低延迟 | gameModeStatus | GameSetFragment.D → H0(6, enable, address) |
| 17 / 0x11 | 设备双连（用户所需的设备管理） | multiConnectStatus | Lc.l.b → H0(17, enable, address) |
| 24 / 0x18 | 高音质音频 | hiQualityAudioStatus | HiQualityAudioItem.setHiResSoundEnable → H0(24, enable, address) |
| 27 / 0x1B | 耳机空间音效开关 | spatialSoundStatus | HeadSetSpatialAudioVM.h → H0(27, false/true, address) |
| 29 / 0x1D | 低音引擎 | bassEngineStatus | 本次仅确认 refreshSwitch 映射 |
| 33 / 0x21 | 游戏 EQ 开关 | gameEqualizerStatus | 本次仅确认 refreshSwitch 映射 |
| 39 / 0x27 | 游戏音效开关 | gameSoundStatus | 本次仅确认 refreshSwitch 映射 |
| 40 / 0x28 | 游戏主开关 | gameModeMainStatus | GameSetFragment.E → H0(40, enable, address) |

这些 ID 是 FeatureSwitchInfo 的 featureId，与能力位序号及独立命令号不同。状态 0 映射关闭、1 映射开启，其余值在 refreshSwitch 中映射未知 -1。设备双连开关只控制双连能力；已配对设备列表、优先级、连接／断连是其他命令，不应从这个开关推导。

## 查询与设置流程

1. 先完成连接与能力查询，确认通用开关协议可用。
2. 发送 `0x010D`，payload 为 `[count, featureId...]`。查询以上八项的 payload 为 `08 06 11 18 1B 1D 21 27 28`。
3. 解析 `0x810D [status, count, (featureId, state)*count]`。仅将返回且状态为 0／1 的项显示为可配置；缺失与其他状态保留为未知／不支持。
4. 发送 `0x0403 [featureId, enabled?1:0]`。例如开双连为 `11 01`，关双连为 `11 00`；开低延迟为 `06 01`。
5. 等待 `0x8403` 成功，再用同一 ID 执行 `0x010D [01, featureId]` 读回确认。

H0(int, boolean, String) → I0(address, featureId, enable, true)，I0 注册等待 command 1027 / 0x0403。证据为 repository-H0.java/json（`ev_1b401dad0b42c74232abcbfabe7ec8dde3ab4e8ce9b4d0b15f6aaa7d90aeb288`）及 repository-I0.java/json（`ev_943bf20499f18aa07b2475ee5dee09707a5883a1a9eab44e7811a867cf629ed0`）；实际两字节封装在相邻 commands/payload2.java/json 的 HeadsetCoreService.j1 中。查询 payload 由父分析的 controls/feature-query.java 确认。

UI 显示游戏主开关与低延迟开关是两个状态；不要让 Python 的“低延迟”默认联动写入 40、39、33。GameSetFragment 在某些型号布局下会处理主开关及音效联动，这不能证明所有型号需要同时写入多个开关。

## 新版空间音效类型命令

HeadSetSpatialAudioVMV2.h 不再写 feature 27，而是调用 repository.u0(type,address)。完整链路确认：

- 设置 `0x0422 [type u8]`，响应命令 `0x8422`。HeadsetCoreService.U0 直接以一个字节发送 type，见 spatial-type-set.java/json，Evidence `ev_33efa919318f3df4b4035a34ab848f0a3245fc439f08873b09494c7b45d41060`。
- 查询 `0x012A`，空 payload；见 spatial-v2-query.java/json，Evidence `ev_dae183c1d7673d35aa4edaa4a73818c70827cae957bce23bb6ee7ab45e700173`。
- 回复 `0x812A [status, type]`，status 为 0 时读取第二字节。源自 commands/receive-parser.smali 的 :pswitch_231；packed-switch 以 0x8100 起始，对应索引 42。Evidence `ev_085cfab5d58a906cf76431b0269881dd3794a3a316364fd90de43a2271c3489a`。
- 能力位 47 同时声明 0x0422 与 0x012A，见 handshake/capability-bits.json。

保留的代码尚未确认 type 数字对应的用户可读标签，不应猜成“固定／头部追踪”等。SDK 可先提供 get_spatial_type() 与 set_spatial_type(type)，并要求调用者使用设备返回或另行验证的枚举。旧 feature 27 与新版类型命令应根据能力和型号数据选择。

另外，spatial-type-query.java/json 是调查中保存的 0x0122 查询；此命令属于能力位 34 的 EQ 路径，不能将它当作新版空间音效查询。新版查询以 spatial-v2-query.java/json 的 0x012A 为准。
